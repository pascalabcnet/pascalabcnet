# План поддержки PascalABC.NET для .NET Framework и .NET 10

## 1. Цель

Из одного репозитория выпускать и проверять две независимые версии PascalABC.NET:

| Линия | Ядро и консольные компиляторы | Графическая оболочка | Назначение |
|---|---|---|---|
| Legacy | `net40` | `net471` (и существующая оболочка для .NET 4.0, где она используется) | Совместимость со старыми компьютерами |
| Modern | `net10.0` | `net10.0-windows` | Современный рантайм и использование возможностей .NET 10 |

`pabcnetc` и `pabcnetcclear` в каждой линии используют одно и то же соответствующее ядро компилятора.

Modern-сборка **не обязана ограничиваться API .NET Framework 4.0**. Общими остаются платформонезависимые алгоритмы, семантическое и синтаксическое деревья. Там, где рантаймы различаются, каждая цель получает собственную реализацию.

## 1.1. Проверенное исходное состояние

- Оба главных решения имеют обычный формат Visual Studio Solution 12.00 и пометку Visual Studio 17. Менять формат `.sln` для двухцелевой сборки не требуется; VS 2026 может открыть и сохранить его без обязательного перехода на `.slnx`.
- Основные `.csproj` уже имеют SDK-style формат (`<Project Sdk="Microsoft.NET.Sdk">`), поэтому их можно расширять до multi-targeting без полного преобразования проектных файлов.
- В `pabcnetc.sln` сейчас 24 C#-проекта, и все они ориентированы на `net40`.
- `VisualPascalABCNET.csproj` ориентирован на `net471`.
- Текущая Windows CI-схема собирает `PascalABCNET.sln`, пересобирает стандартные модули и RTL, использует `sn.exe`/GAC, затем запускает шесть групп `TestSuite` и тесты дополнительных языков.
- Экспериментальный `D:\PABC_Console_Git_NET9` служит источником уже проверенных modern-решений, но не шаблоном для механического копирования: там legacy-цель была `net48`, тогда как основной проект обязан сохранить `net40`.

## 2. Базовые правила архитектуры

1. **Один репозиторий и общие проекты.** Основные SDK-style `.csproj` получают несколько целевых платформ; копии всего исходного дерева для разных рантаймов не создаются.
2. **Явное разделение платформ.** Для условной компиляции вводятся собственные понятные символы, например `PABCNET_LEGACY` и `PABCNET_MODERN`. Встроенные `NET40`, `NETFRAMEWORK`, `NET10_0` можно использовать дополнительно, но код PascalABC.NET не должен зависеть от случайного набора символов SDK.
3. **Минимум директив внутри алгоритмов.** Небольшие различия допустимо оформлять через `#if`. Крупные различия Reflection/Reflection.Emit, загрузки сборок, сохранения PE-файлов и поиска CoreLib выносятся в платформенные классы или partial-файлы.
4. **Современный код имеет право использовать .NET 10.** Если для modern-реализации подходит API .NET 10, он используется непосредственно; эквивалент для `net40` находится в legacy-файле.
5. **Legacy-поведение сохраняется.** Изменение modern-ветки не должно незаметно менять генерацию IL, загрузку модулей или формат артефактов legacy-компилятора.
6. **Артефакты целей не смешиваются.** DLL/EXE, `.deps.json`, `.runtimeconfig.json`, RTL, PCU, временные файлы и результаты тестов разных целей располагаются раздельно.
7. **Каждый этап обратим и проверяем.** Один этап — один небольшой логический набор изменений. Он фиксируется только после прохождения заданного для него контрольного набора сборок и тестов.

## 3. Предлагаемая структура сборки

### 3.1. Проекты

- Проекты ядра и зависимостей консольного компилятора: `TargetFrameworks=net40;net10.0`.
- `pabcnetc` и `pabcnetcclear`: `TargetFrameworks=net40;net10.0`.
- Существующая Windows-оболочка сначала продолжает собираться как `net471` и ссылаться на legacy-ядро.
- Перевод оболочки и плагинов на `net10.0-windows` выполняется отдельным этапом после стабилизации modern-консольного компилятора.
- Проекты, не входящие в фактический граф выбранного продукта, не переводятся заранее «за компанию».

Общие настройки целей, символов, промежуточных каталогов и выходных путей следует централизовать в `Directory.Build.props`/`Directory.Build.targets`, оставляя в `.csproj` только реальные исключения.

### 3.2. Выходные каталоги

На переходном этапе безопаснее сохранить существующий legacy-каталог и создать отдельное modern-дерево:

```text
bin\                 существующая legacy-раскладка
bin-net10\           modern-компилятор и его собственные Lib/RTL/PCU
obj\<project>\net40\
obj\<project>\net10.0\
```

Это уменьшает риск поломки старых скриптов, установщика и оболочки. После полной параметризации сборки можно отдельно решить, стоит ли переименовывать legacy-каталог в `bin-net40`.

Нельзя копировать один и тот же `Lib` или набор PCU одновременно в обе сборки: PCU и скомпилированные стандартные модули должны создаваться тем компилятором и для того рантайма, которому они принадлежат.

## 4. Платформенные границы в исходниках

В первую очередь выделяются места, где .NET Framework и .NET 10 принципиально различаются:

- создание динамической сборки и сохранение PE-файла;
- `AssemblyBuilder`, `ModuleBuilder`, `TypeBuilder` и сопоставление членов constructed generic types;
- работа с CoreLib (`mscorlib` против `System.Private.CoreLib`) и идентичностью загруженных типов;
- разрешение и загрузка ссылочных сборок;
- генерация и использование `.config`, `.deps.json`, `.runtimeconfig.json`;
- BinaryFormatter/устаревшие механизмы сериализации, Remoting, GAC и strong-name-инструменты;
- различия API файловой системы, процессов и кодировок;
- WinForms/WPF и сторонние библиотеки оболочки.

Для `NETGenerator.cs` допускаются точечные условные ветки, если обе реализации относятся к одному IL-алгоритму. Если различается целая операция (например, создание/сохранение сборки), она выносится за интерфейс наподобие `IAssemblyEmitter` или в partial-файлы:

```text
AssemblyEmitter.Legacy.cs
AssemblyEmitter.Modern.cs
NetHelper.Legacy.cs
NetHelper.Modern.cs
```

Названия окончательно выбираются после инвентаризации кода. Не следует механически дробить `NetGenerator.cs`, пока не определены устойчивые границы.

## 5. Этапы работы

### Этап 0. Зафиксировать исходную точку

1. Собрать чистый legacy-репозиторий средствами VS 2026/.NET SDK 10 без изменения целевых платформ.
2. Проверить отдельно `pabcnetc.sln` и полный `PascalABCNET.sln`.
3. Запустить существующие тестовые скрипты и сохранить перечень уже существующих сбоев, длительность и требования окружения (GAC, `sn.exe`, `gacutil`, NUnit/Helix).
4. Определить минимальный граф проектов для двух консольных компиляторов.

**Контрольная точка:** воспроизводимая legacy-сборка и известный baseline тестов. До этого перенос modern-кода не начинается.

### Этап 1. Создать двухцелевой каркас консольного компилятора

1. Добавить централизованные настройки `net40;net10.0` только для минимального графа `pabcnetc.sln`.
2. Развести `bin`, `bin-net10` и `obj`.
3. Ввести `PABCNET_LEGACY`/`PABCNET_MODERN`.
4. Добиться компиляции обоих графов без переноса функциональных исправлений из экспериментального проекта.

**Контрольная точка:** обе цели собираются независимо; повторная сборка одной цели не меняет артефакты другой; legacy smoke-тест не ухудшился.

### Этап 2. Перенести проверенный modern-слой генератора

1. Сравнить `D:\PABC_Console_Git_NET9` с исходным репозиторием по отдельным изменениям, а не копировать его рабочее дерево целиком.
2. Перенести modern-реализации из `NetGenerator.cs`, `NetHelper.cs` и связанных участков TreeConverter.
3. Сохранить исходные реализации .NET Framework под legacy-веткой.
4. Для каждого перенесённого исправления добавить минимальный регрессионный Pascal-тест.

Первая обязательная группа регрессий:

- `List<enum>` и конструкторы generic-типов с перечислением;
- многомерный generic-массив `array[,] of T`;
- `foreach` по массиву перечислений;
- выбор `Task<T>.Run` с лямбдой;
- уже обнаруженные различия generic MemberInfo/Reflection.Emit.

**Контрольная точка:** modern smoke-набор проходит, а те же языковые тесты продолжают проходить в legacy.

### Этап 3. Разделить рантайм и стандартные модули

1. Определить полный состав файлов `bin\Lib`, которые являются общими исходными ресурсами, и файлов, которые являются платформенными результатами сборки.
2. Параметризовать сборку RTL и стандартных Pascal-модулей.
3. Исключить использование GAC modern-линией; legacy-процесс пока оставить без функциональных изменений.
4. Настроить modern runtimeconfig/deps и поиск системных сборок .NET 10.
5. Проверить, что CoreLib не загружается повторно в несовместимом контексте и что кэш NetHelper учитывает реальную идентичность сборки, а не только путь/дату файла.

**Контрольная точка:** обе версии компилируют и запускают программы только со своим RTL/Lib; перекрёстное загрязнение каталогов невозможно.

### Этап 4. Параметризовать систему тестирования

1. Сделать target-aware запуск существующего `TestRunner` без дублирования каталога `TestSuite`.
2. Передавать тестам путь к выбранному компилятору и отдельный каталог результатов.
3. Разделить наборы:
   - быстрый smoke;
   - регрессии миграции;
   - полный `TestSuite`;
   - дополнительные языки;
   - тесты, требующие Windows/GAC/GUI.
4. В отчёте явно различать ошибку компиляции Pascal, внутреннюю ошибку компилятора, ошибку запуска и несовпадение вывода.
5. Не считать тест успешным только потому, что компиляция завершилась без исключения: где предусмотрено, запускать полученный EXE и проверять результат.

**Контрольная точка:** одной командой можно независимо прогнать `net40` и `net10.0`, результаты не перезаписывают друг друга.

### Этап 5. Полная стабилизация консольных компиляторов

1. Последовательно устранить различия полного набора тестов.
2. Каждую найденную ошибку сначала уменьшать до отдельного теста.
3. Исправления классифицировать как:
   - общая ошибка компилятора;
   - modern-совместимость;
   - допустимое различие рантаймов;
   - внешний/устаревший компонент.
4. Проверить clean build и rebuild обеих целей в разном порядке.

**Контрольная точка:** полный согласованный набор тестов проходит для обеих целей либо имеет документированный короткий список осознанных исключений.

### Этап 6. Перевести modern-оболочку и плагины

1. Построить граф зависимостей `VisualPascalABCNET` и разделить компоненты на:
   - совместимые с `net10.0-windows`;
   - требующие обновления/замены;
   - только legacy (Remoting, старый дизайнер, старые плагины и т. п.).
2. Добавить modern-цель оболочке только после готовности modern-ядра.
3. Переводить плагины группами, сохраняя legacy-цели там, где они нужны старой оболочке.
4. Провести ручные сценарии: запуск, компиляция, выполнение, отладка, подсказки, подключение модулей и плагины.

**Контрольная точка:** modern-оболочка использует именно modern-ядро; legacy-оболочка продолжает использовать legacy-ядро.

### Этап 7. CI и выпуск

1. Создать Windows-матрицу минимум из `legacy-console`, `modern-console`, `legacy-full`, `modern-full`.
2. Быстрые проверки выполнять на каждый push/PR, полный набор — по согласованному расписанию и перед выпуском.
3. Обновить GitHub Actions до актуальных поддерживаемых версий только отдельным изменением.
4. Выпускать два явно названных комплекта артефактов и не собирать их из общего загрязнённого `bin`.
5. Проверять запуск на машине без установленного SDK: legacy с требуемым .NET Framework, modern как framework-dependent и/или self-contained пакет — решение принимается после измерения размера и требований установки.

**Контрольная точка:** воспроизводимый CI создаёт два устанавливаемых продукта из одного commit.

### Этап 8. Документация и сопровождение

1. Описать требования к VS 2026, .NET 10 SDK и targeting packs .NET Framework 4.0/4.7.1.
2. Записать команды сборки и тестирования каждой цели.
3. Описать правила добавления platform-specific кода.
4. Ввести короткий checklist для изменений `NetGenerator`/`NetHelper`: сборка обеих целей, smoke обеих целей, соответствующие регрессии.

## 6. Порядок фиксации изменений

Предпочтительная последовательность небольших commit:

1. только инфраструктура целей и каталогов;
2. только минимальные platform stubs для успешной компиляции;
3. перенос одной группы Reflection.Emit/типовых исправлений вместе с её тестами;
4. разделение RTL/Lib/PCU;
5. параметризация TestRunner и скриптов;
6. оставшиеся группы совместимости;
7. оболочка и плагины — отдельными сериями;
8. CI, упаковка и документация.

Нельзя объединять массовое форматирование, переименование каталогов и функциональную миграцию в один commit: это затруднит сравнение с исходной .NET Framework-версией и поиск регрессий.

## 7. Критерии готовности проекта

- Из чистого checkout одной документированной командой собирается legacy-продукт и другой командой modern-продукт.
- `net40`-ядро не получает зависимостей от API более новых версий Framework.
- `net10.0`-ядро реально работает на .NET 10 и может использовать его API, а не запускает legacy-сборки через совместимость.
- Две версии не разделяют бинарные RTL/PCU и не загрязняют результаты друг друга.
- Оба консольных компилятора проходят согласованный полный набор тестов.
- Legacy GUI работает с legacy-ядром; modern GUI — с modern-ядром.
- CI собирает и сохраняет оба комплекта артефактов.

## 8. Ближайший следующий шаг

Выполнить только **этап 0**: снять чистый baseline текущего `net40`/`net471`, построить точный граф `pabcnetc.sln` и записать фактические команды и результаты. До завершения baseline не менять целевые платформы и не переносить код из экспериментального проекта.
