# NuGetRestoreTests

Интеграционный тест NuGet-моста и его использования modern IntelliSense.

Из корня репозитория:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release
```

Fixtures/TestRoot, Fixtures/TestRootV2 и Fixtures/TestDependency собираются автоматически.
Сам тест через NuGet.Packaging создаёт локальный feed с пакетами и восстанавливает
их через API PascalABCNet.PackageServices. Для root используется настоящая
reference assembly, созданная C#-компилятором, и отдельная runtime implementation.
Выполнение теста не обращается к nuget.org и не запускает restore через CLI.

Повторная проверка выполняется в самостоятельно созданной копии текущего
.NET runtime без sdk/, с пустым PATH. Она проверяет, что --list-sdks пуст,
и повторяет весь набор сценариев без установленного в этом окружении SDK.

Проверяются также стандартная иерархия NuGet.Config, локальный источник
с именем intranet, отключённые источники, `<clear/>`, NUGET_PACKAGES,
приоритет явного API-каталога и отдельный скрытый кеш на программу.
Настройки теста создаются в его временном каталоге; пользовательские конфиги
не меняются. Переменная NUGET_PACKAGES восстанавливается после проверки.

Отдельно проверяются источник nuget.org по умолчанию без настроенных источников,
чистый пользовательский профиль без готового NuGet.Config и пустой PATH,
сохранение явных источников и запретов (`<clear/>`, пустая секция, отключённые
источники), отсутствие перезаписи конфигов. Сеть для этих проверок не нужна.
Отдельный запуск: `NuGetRestoreTests --source-defaults`.

Явный дополнительный тест общего кеша и скачивания с nuget.org:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -- --shared-cache
```

Для него нужен установленный Newtonsoft.Json 13.0.3. Dapper 2.1.66
скачивается при отсутствии либо используется из кеша. Источники берутся из
настоящих настроек NuGet; nuget.org должен быть включён. Существующие пакеты
не удаляются и не изменяются. Этот режим требует сеть при первом скачивании.

В том же режиме восстанавливается реальный пакет
Microsoft.Extensions.Configuration.Json 10.0.0: проверяются зависимость второго
уровня через Configuration.FileExtensions к FileProviders.Physical, наличие всех
выбранных DLL и повторный no-op restore. Скачанные пакеты остаются в общем кеше.

Обычный режим также проверяет IntelliSense на локальном тестовом пакете:
completion, hover и подсказку параметров для корневой DLL, completion для
транзитивной DLL, удаление `{$package}`, ошибочную версию и восстановление
анализа после исправления. Те же три запроса и смена версии DLL через
`didChange` проверяются через настоящий LSP-сервер по stdin/stdout.
Там же проверяется замена обычной DLL по `{$reference}` и повторный запрос
completion без изменения исходного `.pas`.
Для этого не требуется сеть, но нужен собранный
`bin-net10/PascalABCNet.LanguageServer.dll`.

Пакеты из Pascal-модулей также проверяются в обычном прогоне. Отдельный запуск:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -- --module-intellisense
```

Проверяются completion, hover и параметры для пакета, объявленного только в
модуле; вложенные `uses`, `uses ... in`, секция implementation, допустимый цикл
модулей, несохранённый и ещё не существующий на диске модуль. Изменение пакета,
удаление директивы, ошибка восстановления и конфликт с `reference` не оставляют
старые подсказки. Проверяются запрет замены уже выбранной транзитивной версии,
восстановление после ошибки, разные графы у программ с общим исходником модуля,
изменение файла на диске без правки главной программы, а также PCU без исходника.
Те же запросы и изменения открытого модуля проверяются через настоящий LSP.
Используются только локальные тестовые пакеты, без сети.

Для проверки отдельной подготовленной сборки можно задать
`PABC_NUGET_TEST_COMPILER_DIR`: каталог с компилятором, LanguageServer, Lib и Lng.

Обычный прогон также проверяет переключение версии DLL 1.0.0 → 1.1.0 →
1.0.0 в одном долгоживущем IntelliSense-процессе. Затем два одновременно
открытых документа с разными версиями по очереди запрашивают completion:
их DOM пересоздаётся при смене поколения сборок. Отдельно проверяются два
экземпляра LanguageServices в одном процессе. Вариант 1.1.0 собран из
другого исходника с членом `OnlyInV2`, поэтому тест обнаруживает повторное
использование старой сборки.

Необязательная проверка раннего восстановления пакетов самим modern-компилятором
из главного `.pas` (без сети, на локальном тестовом feed):

```bat
dotnet build pabcnetc_clear\PABCNETCclear.csproj -f net10.0 -c Release
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -- --compiler
```

Проверяются две директивы `{$package}` в одной программе, общий граф зависимостей,
доступность типов пакета и его транзитивной зависимости в главной программе
и в подключённом Pascal-модуле, повторная компиляция с чтением PCU,
конфликт версий с указанием второй строки и ошибка отсутствующего пакета.
Также проверяются реальный запуск `dotnet` с транзитивной зависимостью,
два EXE с разными версиями пакета в общем `net10-output` и удаление ранее
созданного `.deps.json` после перекомпиляции программы без `{$package}`.
Для семантики пока используются runtime-DLL: существующий Reflection-загрузчик
не может загрузить NuGet `ref/`-сборку. Для запуска компилятор создаёт
`<программа>.deps.json` и добавляет путь общего кеша NuGet в
`<программа>.runtimeconfig.json`; пакетные DLL рядом с EXE не копируются.
Нативные файлы Windows x64 поддерживаются отдельными проверками ниже;
resource assemblies пока не поддерживаются.
Modern-эквиваленты legacy-тестов `directive_package_same_version.pas`,
`usesunits/use_directive_package.pas` и
`errors/err_directive_package_unit_conflict.pas` также включены в `--compiler`.
Тест читает исходные примеры из `TestSuite`, заменяет фиктивный `Example.Package`
на локальный `PascalABC.TestRoot` с версиями 1.0.0/1.1.0 и компилирует отдельные
копии. Проверяются регистронезависимое объединение одинаковых директив,
совпадение версии в программе и модуле, повторная компиляция и конфликт версий.
В `project.assets.json` проверяются выбранные версии и единственный источник —
локальный feed. Исходные примеры остаются в legacy-прогоне без изменений;
эти примеры и вспомогательный `units/u_directive_package.pas` исключены из общего modern-прогона, чтобы он не обращался к
nuget.org за несуществующим тестовым пакетом.

Временные modern-копии размещают `{$package}` до кода, включая `unit` и `uses`.
Для проверки отдельно собранного компилятора можно задать
`PABC_NUGET_TEST_COMPILER_DIR` — каталог с `pabcnetcclear.exe`, его DLL и `Lib`.
Без этой переменной используется обычный `bin-net10`.

Для отдельного запуска только локального restore и этих compiler-проверок:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -- --package-directives
```

### Пакеты, объявленные в модулях (.NET 10)

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --module-packages
```

Этот набор также включён в `--compiler`. Он использует только локальные тестовые
пакеты и отдельный временный кеш, без сети и изменений пользовательских настроек.
В общем прогоне он работает отдельным процессом, как компилятор в рабочей схеме:
ссылки из ранее проверенных DOM IntelliSense не должны мешать выгрузке его DLL.
Дополнительный `Fixtures/TestDependencyV2` — DLL с тем же внутренним именем,
но другим содержимым для проверки транзитивных конфликтов.

Проверяются:

- пакет только в модуле, вложенные `uses` в interface/implementation, модуль в другой папке;
- повторение одинаковой версии в программе и модулях без повторного восстановления;
- расширение графа совместимым пакетом и совместное разрешение требований одного файла;
- предупреждение при выборе общей версии для разных совместимых ограничений;
- отказ менять уже выбранную прямую или транзитивную версию между модулями;
- конфликт с `{$reference}` в обоих порядках, в том числе по зависимости DLL;
- допустимость одинаковых копий DLL из пакета и явной ссылки;
- повторная компиляция и запуск только по PCU, когда исходники модулей скрыты;
- конфликт с пакетом из PCU без перезаписи предыдущего EXE;
- публикация программы с пакетом только в модуле и запуск при недоступном кеше;
- один экземпляр компилятора: ошибка, успешная следующая сборка, смена версии
  между отдельными компиляциями и удаление пакетов вместе с модулем.

`{$package}` пишется до `unit`/`program` и любого `uses`. Требования очередного
файла обрабатываются до его семантики; предварительного обхода исходников нет.
Источники и кеш выбираются по настройкам главной программы для единого графа.
В PCU используются уже сохранённые директивы, без изменения формата файла.
Сборки родительского PCU читаются после требований его зависимостей, до чтения
его типов. Все новые DLL проверяются вместе с накопленными явными ссылками
и их зависимостями; конфликт не вызывает подмену DLL или продолжение компиляции.

Это этап компилятора. Сбор требований из модулей во внешнем IntelliSense
в этот набор изменений не входит.

Режим `--compiler` дополнительно публикует обе версии тестового пакета в
`publish/<имя программы>/`, повторяет публикацию и запускает оба EXE при
временно недоступном NuGet-кеше. Публикуются managed DLL и выбранные native-файлы
Windows x64; resource assemblies пока не поддерживаются. Также проверяются программа без пакетов, явная
`{$reference}` и отказ заменять папку, в которую пользователь добавил файл.

Отдельная проверка цепочки Run10 через долгоживущий Controller/Worker
(после сборки `Net10Runtime.slnx` в `bin-net10`):

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -- --controller
```

Она передаёт `{$package}` из снимка открытого редакторского документа,
компилирует две версии пакета одним Worker и запускает обе программы с
`__RedirectIOMode` и общим `net10-output`. Затем удаляет директиву из
снимка, проверяет очистку `.deps.json` и повторный запуск. Сеть не нужна.
Дополнительно проверяется команда `publish=true`: Worker собирает снимок без
`__RedirectIOMode`, создаёт папку публикации и программа запускается без кеша.

Ожидаемый результат обычного режима: строки PASS и код завершения 0.
Версии зависимостей тестового приложения зафиксированы в packages.lock.json.

## Нативные зависимости Windows x64

Обычный прогон также создаёт локальные тестовые пакеты с вариантами `win-x64`,
`win-x86`, `linux-x64` и fallback `win`. Без сети проверяются выбор нужного RID,
замена управляемой реализации на платформенную, отделение native-файлов от
семантических ссылок, повторный no-op restore и переносимость чисто управляемых
пакетов. Официальный portable RID graph встроен в DLL и работает без SDK.
Проверяются native-секция `.deps.json`, публикация, отсутствие файлов, запрет
выхода за каталог пакета и сохранение предыдущей публикации/manifest при ошибке.

Отдельный быстрый запуск:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --native-assets
```

Реальный интеграционный тест требует Windows x64 и сеть к nuget.org:

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --sqlite-native
```

Он скачивает Microsoft.Data.Sqlite 10.0.13 в отдельный временный кеш, компилирует
Pascal-программу и выполняет `select 40 + 2` через настоящую нативную SQLite.
Проверяются no-op restore, отсутствие копирования пакетных DLL к EXE, ошибка
при удалённой `e_sqlite3.dll` и восстановление после её возврата, запуск без SDK
и с пустым PATH, completion/hover без загрузки SQLite в процесс IntelliSense,
публикация и выполнение при недоступном кеше. Кеш пользователя не переименовывается
и не изменяется; тестовый кеш удаляется. Сеть не включена в обычный прогон.
Можно задать `PABC_NUGET_TEST_COMPILER_DIR` для отдельно собранного modern-комплекта.

### Math.NET Numerics + Intel MKL

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --mathnet-mkl
```

Windows x64, сеть к nuget.org; отдельный временный кеш без изменения кеша
пользователя. Восстанавливается MathNet.Numerics.MKL.Win-x64 3.0.0 с
MathNet.Numerics и MathNet.Numerics.Providers.MKL 5.0.0. Пакет нативной части
имеет размер около 53 МБ. В обычный локальный прогон сетевой тест не входит.

Компилируется сохранённый пример `NuGet/Samples/MathNetMkl.pas`. Он вызывает
`Control.UseNativeMKL` (ошибка, а не fallback при отсутствии MKL), проверяет
конкретный тип провайдера и умножает две матрицы. Ожидаемый результат:
`19 22 43 50`. Дополнительно проверяются:

- no-op restore и отсутствие копирования DLL рядом с исходным EXE;
- запуск с изолированным .NET runtime без SDK и с пустым PATH;
- обязательность обеих DLL: `libMathNetNumericsMKL.dll` и `libiomp5md.dll`;
- отказ при удалении каждой из них, восстановление после возврата;
- completion, hover и параметры без загрузки MKL/OpenMP в процесс IntelliSense;
- публикация и исполнение при недоступном кеше, без SDK и PATH.

Замер скорости не является критерием корректности этого теста.

### ML.NET: SDCA-регрессия

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --mlnet-regression
```

Windows x64, nuget.org, отдельный временный кеш; сетевой тест не входит в обычный
прогон. Компилируется `NuGet/Samples/MLNetRegression.pas` с Microsoft.ML 5.0.0
и транзитивными Microsoft.ML.CpuMath/DataView. Программа обучает SDCA на 41 точке
`y = 2*x + 1`, делает прогнозы для -1.25, 0.5, 1.75. Независимо от Pascal Assert
тестер проверяет конечность чисел и отклонение от -1.5, 2, 4.5 менее 0.1.
Это тест корректности, не скорости или качества на реальных данных.

Проверяются no-op restore, отсутствие DLL рядом с исходным EXE, выбор системной
System.Collections.Immutable вместо старой пакетной копии, обучение с пустым
PATH и без SDK, сохранение модели и чтение в новом процессе без переобучения,
completion/hover/signature help без загрузки native DLL в процесс IntelliSense.
Публикация проверяется при переименованном тестовом кеше, без SDK и PATH:
как обучение, так и прогноз по сохранённой модели. `regression.zip` — файл данных,
его тест явно копирует в публикацию; автоматически публикуются только зависимости.

В выбранном графе из нативных файлов есть `LdaNative.dll`.
Она публикуется, но SDCA её не вызывает;
тест не заявляет проверки LDA, LightGBM, ONNX, TensorFlow или всего ML.NET.

### Копии базовых сборок в пакетах (без сети)

`--framework-assemblies` проверяет `FrameworkAssemblyPolicy`: платформенная
сборка исключает лишь совпадающие по identity пакетные копии с не большей версией.
Более новая assembly version, другое имя/culture/ключ, unsigned или переименованная
чужая DLL сохраняются. Native assets не фильтруются. Проверяются согласованность
compile/runtime/manifest и no-op restore. Искусственные DLL здесь содержат
только тестовые метаданные, не загружаются и не исполняются.
Проверки включены также в обычный прогон и повтор без SDK.

### ML.NET + нативный LightGBM (Windows x64)

```bat
dotnet run --project tests\NuGetRestoreTests\NuGetRestoreTests.csproj -c Release -p:PABCNET_LEGACY_ONLY=false -- --lightgbm-native
```

Требует nuget.org, использует отдельный временный кеш, не входит в обычный
локальный прогон. Можно задать `PABC_NUGET_TEST_COMPILER_DIR` для отдельного
подготовленного комплекта компилятора. Кеш пользователя не переименовывается.

Компилируется `NuGet/Samples/LightGbmRegression.pas` с Microsoft.ML.LightGbm 5.0.0,
Microsoft.ML/FastTree 5.0.0 и LightGBM 4.6.0. Нативные файлы выбранного графа:
`lib_lightgbm.dll`, `lightgbm.exe`, `LdaNative.dll`, `FastTreeNative.dll`.
Утилита `lightgbm.exe` не запускается: обучение использует DLL через ML.NET API.

Проверки:

- no-op restore, win-x64 assets, отсутствие копирования DLL к исходному EXE;
- обучение на 401 точке `y = x²`, фиксированные seed и один поток;
- прогнозы в новых точках -1.255, 0.505, 1.755 внутри обученного диапазона;
  тестер независимо проверяет конечность чисел и отклонение менее 0.15;
- фактическая загрузка `lib_lightgbm.dll` из точного пути пакета, а при публикации —
  из опубликованной папки (не из чужой установки или PATH);
- обучение/сохранение, загрузка и тот же прогноз в новых процессах без SDK и PATH;
- ошибка при отсутствующей DLL в тестовом кеше и восстановление после возврата;
- completion, hover и параметры `Fit` без загрузки native DLL в IntelliSense;
- публикация всех выбранных native assets; обучение и загрузка модели при
  недоступном тестовом кеше, без SDK и PATH;
- в публикации без `lib_lightgbm.dll` обучение падает, но прогноз по сохранённому
  дереву работает без её загрузки; после возврата DLL обучение восстанавливается.

Важное различие: при запуске из кеша хост .NET заранее требует файлы из `.deps.json`,
даже если конкретный код их не вызовет. Поэтому настоящий отказ нативного обучения
проверяется также в опубликованной папке без cache-bound manifest. Прогноз по готовой
модели сам по себе не считается доказательством нативного обучения. Файл модели
`lightgbm.zip` тест явно копирует как данные пользователя, а не как NuGet-зависимость.
Пустой PATH не скрывает системные библиотеки Windows; это не тест на чистой ОС.
Это тест корректности регрессии, не скорости, всех тренеров или других платформ.

### Одновременный restore компилятора и IntelliSense

`--restore-concurrency` — локальный тест без сети. Два процесса восстанавливают
разные версии одного тестового пакета в общий RestoreDirectory, затем то же
делают два параллельных клиента внутри процесса. Проверяются версия и содержимое
возвращённой DLL: нельзя прочитать чужой граф или потерять `project.assets.json`.
На старой реализации тест воспроизводил чтение графа другого клиента.

`PackageRestoreService` использует штатную межпроцессную блокировку NuGet на
конкретный каталог: она охватывает restore и полное чтение его результата.
Разные каталоги не объединены глобальной блокировкой. Файлы блокировок находятся
в служебной временной папке NuGet, не рядом с пользовательским исходником.
Проверяются отмена ожидания занятого каталога и успешный no-op после освобождения.
Тест включён в обычный прогон и повтор без SDK. Один лишь `DisableParallel` внутри
NuGet restore не синхронизирует отдельные процессы компилятора и IntelliSense.
