# Диагностика поиска MessageBox

Запуск на Windows с подготовленными `bin` и `bin-net10`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/MessageBoxLookupTests/Test-MessageBoxLookup.ps1
```

Тест не запускает графические программы и нативный MessageBox: выполняется
только компиляция `/pcuonly`. Все копии и результаты создаются в `.codex-build`.
Рабочие исходники и PCU стандартных модулей не изменяются.

Проверяются отдельный WinForms, WPF/WinForms в обоих порядках, нативная
одноимённая функция и исходные RobotField/PT4MakerNetX без полного имени.
Каждый случай имеет отдельный процесс и каталог, включая разделение net472/net10.
В холодных копиях modern-комплекта нет готовых PCU.

## Установленная причина до исправления

Трассировка холодной сборки полного bootstrap показала:

1. При компиляции реализации PT4TaskMakerNET поиск его нативной функции
   MessageBox также обращается к .NET-области имён.
2. WinForms в этот момент ещё не загружен. `NetHelper.FindType(name, namespaces)`
   записывает `FoundInfo(false)` в общий `type_search_cache["MessageBox"]`.
3. После загрузки WinForms `types["MessageBox"]` уже содержит `TypeInfo`,
   но отрицательная запись остаётся: `init_namespaces` обновляет индекс типов,
   не отменяя этот результат поиска.
4. Следующий вызов FindType немедленно возвращает null по `!fi.exists`,
   даже если новый список uses содержит System.Windows.Forms.

Это не конфликт WPF и WinForms: простые смешанные примеры проходят.
У обычного и modern-bootstrap различаются состав и порядок зависимостей;
ошибка проявляется, когда первый промах произошёл до загрузки нужной DLL.
Готовый PCU также меняет сценарий: тело нативного вызова уже не компилируется.

## Почему обычная сборка проходила

`Compiler.CompileInterfaceDependencies` обходит uses с последнего элемента
к первому (`Compiler.cs`, цикл от `interfaceUsesList.Count - 1 ...` к нулю).
В обычном `RebuildStandartModules.pas` FormsABC и другие графические модули
расположены правее PT4MakerNetX/PT4TaskMakerNET. Они успевают подключить WinForms
до компиляции нативного вызова MessageBox из PT4TaskMakerNET.

При добавлении модулей в `RebuildStandartModulesNet10.pas` блок PT4 был помещён
правее FormsABC/Robot/GraphWPF. Поэтому PT4TaskMakerNET обрабатывается раньше
графического блока: промах появляется до индексирования WinForms.
Это изменение порядка в сборочной программе, а не различие правил .NET.

До исправления отдельный `Test-MessageBoxLoadOrder.ps1` подтвердил без инструментализации:

- настоящая холодная обычная сборка Framework проходит;
- холодная сборка нового modern-списка падает с MessageBox на обеих платформах;
- тот же список с GraphABC в правом конце проходит на обеих платформах.

Трассировка диагностических копий DLL также показала одинаковую последовательность
на обеих платформах: при сбое сначала `FIRST MESSAGEBOX index=none`, затем
`INDEX WINFORMS cache=False`; при успешном порядке сначала
`INDEX WINFORMS cache=none`, затем `FIRST MESSAGEBOX index=TypeInfo`.
В настоящей обычной сборке индекс WinForms тоже заполнен до первого поиска.
Временная трассировка удалена из исходников; рабочие компиляторы не заменялись.

## Исправление и регрессии

Оба пути `NetHelper.FindType` сохраняют отрицательные результаты для текущего
индекса типов. При индексировании новой DLL удаляются только промахи;
положительный кеш и кеши членов сохраняются. Повторное подключение уже
проиндексированной DLL ничего не очищает. AddType и прямое разрешение CLR-типа
адресно отменяют промах для добавляемого имени. Индексированный список
одноимённых типов не кешируется как отсутствие имени.
Общий поиск перегрузок и порядок uses не менялись.

Оба скрипта теперь требуют успешной компиляции всех вариантов, включая холодный
bootstrap с короткими именами MessageBox. У `Test-MessageBoxLoadOrder.ps1` есть
необязательные параметры `-LegacyTreeConverterPath` и `-ModernTreeConverterPath`
для проверки новых DLL только в изолированных копиях, без замены рабочих bin.

Дополнительный независимый тест `tests/TypeLookupCacheTests` проверяет оба пути
поиска, повторное использование промахов, поздние и повторно подключаемые сборки,
совпадающие короткие имена, границы uses, регистр, сохранность положительного
кеша и таблиц членов на net472/net10.
