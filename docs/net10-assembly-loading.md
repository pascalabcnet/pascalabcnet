# Загрузка и перезагрузка DLL в PascalABC.NET под .NET 10

## Что сделано

В modern-версии компилятора для .NET 10 подключаемые пользовательские DLL теперь
загружаются через отдельный выгружаемый `AssemblyLoadContext`.

Раньше сборки, загруженные обычным `Assembly.Load*`, оставались в процессе до его
завершения. Для долгоживущего процесса компилятора это означало, что после
перекомпиляции пользовательской DLL могла продолжать использоваться её старая версия.

Теперь компилятор:

1. хранит пользовательские DLL и их зависимости в отдельном контексте
   `PABC.ReferenceAssemblies`;
2. перед новой компиляцией проверяет, изменились ли загруженные файлы;
3. при изменении очищает связанные с прежними `Type`, `MemberInfo` и `Assembly`
   кеши компилятора;
4. выгружает старый `AssemblyLoadContext`;
5. создаёт новый контекст и загружает актуальные версии DLL.

Механизм включён по умолчанию только для сборки `PABCNET_MODERN` (.NET 10).
Переменная окружения для его включения больше не нужна. Сборка компилятора под
.NET Framework 4.0 продолжает использовать прежний механизм.

## Какие сборки выгружаются

- Пользовательские DLL, подключённые директивой `{$reference ...}`.
- Их локальные транзитивные зависимости, найденные рядом с корневыми DLL или в
  каталогах остальных подключённых сборок.
- DLL, сведения о которых были сохранены в PCU.

Системные сборки установленного .NET runtime не загружаются в пользовательский
контекст и живут вместе с процессом компилятора. Это относится и к системной DLL,
подключённой явно, даже если её нет в небольшом списке неявных корневых ссылок.

## Обнаружение изменений и кеширование

В обычной повторной компиляции неизменившиеся DLL не перечитываются полностью.
Для быстрой проверки используются путь, размер и время изменения файла.

Метаданные сборки кешируются. SHA-256 вычисляется только тогда, когда встретились
несколько файлов с одинаковым внутренним именем сборки и необходимо отличить
идентичные копии от конфликта. Поэтому обычный проект с большим числом разных,
неизменившихся DLL не получает массового пересчёта хешей.

Команда `Rebuild` принудительно начинает новое поколение ссылок. Это покрывает
случай, когда средство сборки заменило DLL, сохранив её размер и время изменения.

## Конфликты сборок

Компилятор проверяет не только имена файлов, но и внутреннюю identity сборки.

- Две побайтово одинаковые копии одной DLL разрешены и дедуплицируются, даже если
  один из файлов переименован.
- Разные DLL с одним внутренним simple name отвергаются нормальной диагностикой.
- Разные `AssemblyVersion` при одном simple name также нельзя использовать
  одновременно без механизма assembly aliases.
- Конфликт двух разных поколений общей транзитивной зависимости обнаруживается
  независимо от порядка загрузки корневых DLL.

`AssemblyLoadContext` решает замену DLL между последовательными компиляциями, но
не делает две несовместимые версии одной сборки одновременно доступными одной
программе.

## Работа с PCU

Проверены следующие случаи:

- директива `{$reference}` находится в Pascal-модуле;
- модуль компилируется в PCU, после чего его исходник удаляется;
- неизменившийся PCU связывается с новой версией внешней DLL;
- два разных PCU используют одну внешнюю DLL;
- относительный путь к DLL в PCU разрешается относительно расположения PCU.

PCU остаётся кешем компиляции и не фиксирует старую загруженную `Assembly` в памяти.

## Специализированные интеграционные тесты

Основной тест находится в:

```text
tests/CompilerAssemblyReloadTest
```

Обычный запуск:

```bat
dotnet run --project tests\CompilerAssemblyReloadTest\CompilerAssemblyReloadTest.csproj -- bin-net10\pabcnetc.dll
```

Нагрузочный запуск с 50 последовательными заменами DLL:

```bat
dotnet run --project tests\CompilerAssemblyReloadTest\CompilerAssemblyReloadTest.csproj -- bin-net10\pabcnetc.dll --stress
```

Тесты работают с одним долгоживущим процессом компилятора и проверяют:

- замену корневой DLL по тому же пути;
- замену прямой и транзитивной зависимости;
- цепочку `Root -> Common -> Leaf`;
- общую зависимость нескольких корневых DLL;
- возврат от новой версии к старой без оставшихся метаданных;
- десять повторных компиляций неизменившегося графа без повторного чтения PE и
  без создания нового контекста;
- принудительную перезагрузку при `Rebuild` с сохранёнными размером и временем DLL;
- смену каталогов ссылок, исходников, рабочего каталога и output;
- абсолютные, простые относительные и родительские относительные пути;
- пути с пробелами и русскими символами;
- исчезновение зависимости и успешное восстановление в том же процессе;
- повреждённую корневую DLL и восстановление после нормальной диагностики;
- удалённую корневую DLL и восстановление без перезапуска компилятора;
- одинаковые копии сборки и конфликты одинаковых внутренних имён;
- конфликт поколений в ромбовидном графе зависимостей;
- PCU с внешними ссылками и замену DLL без пересоздания PCU;
- явную системную DLL `System.Reflection.Metadata.dll`, отсутствующую в корневом
  списке: она компилируется и не попадает в выгружаемый пользовательский контекст;
- успешную выгрузку старого контекста через `WeakReference` и GC;
- отсутствие заметного накопления памяти после 50 замен DLL.

В выполненном нагрузочном тесте private memory процесса после прогрева изменилась
примерно со 108 до 106 МБ, то есть накопления старых поколений DLL не обнаружено.

## Исправление удержания контекста в IntelliSense при повторном restore

Сценарий: открыть программу с ML.NET, при работающем LanguageServer убрать
её отдельный кеш `packages`, изменить текст и повторить восстановление.
При повторных сменах поколения проверка обнаруживала невыгруженный старый контекст.

Причина установлена через `dotnet-dump` и `gcroot`, а не предположением:
`CompilerReflectionCacheState.Members` → таблица членов системного
`Dictionary<,>` → `Newtonsoft.Json.Linq.Extensions.AsJEnumerable` → старый
`LoaderAllocator`. Системный ключ не принадлежит выгружаемой сборке,
но в его таблице лежат extension-методы этой сборки.

Теперь при точечной очистке проверяются также значения `Members` и кешей
методов/конструкторов/полей по handle, а также типы в `EntryTypes`.
Проверка члена учитывает `ReflectedType`: унаследованный метод может быть
объявлен в `System.Object`, но отражён через пользовательский тип.
Таблица членов с пакетными ссылками удаляется и строится заново при обращении;
обычные системные записи, не содержащие таких ссылок, сохраняются.

`VerifyPreviousGenerationWasUnloaded` не изменён и не отключён.
Добавлен прямой тест точечной очистки с реальным `WeakReference`, который
падает на старом коде и проходит после исправления. Автономный LSP-тест
несколько раз убирает локальный кеш с extension-методом для `System.Object`;
отдельный тест повторяет сценарий с Microsoft.ML.TimeSeries/Mkl.Redist 5.0.0,
чередуя немедленный запрос подсказки и фоновый анализ после debounce.

Команды и детали: `tests/CompileNet10.Tests/NuGetProgress.md`.

## Основные файлы реализации

Результаты последующей проверки остальных кешей и исправление двух цепочек
удержания пользовательского enum: [аудит значений кешей](net10-cache-value-audit.md).

- `TreeConverter/NetWrappers/CollectibleReferenceManager.cs` — жизненный цикл
  выгружаемого контекста, поиск зависимостей, fingerprints и проверка identity.
- `TreeConverter/NetWrappers/CompilerReflectionCacheState.cs` — собранные в одном
  месте reflection-кеши компилятора и очистка ссылок на выгружаемую сборку.
- `TreeConverter/NetWrappers/NetHelper.cs` — выбор постоянного или выгружаемого
  контекста и переключение поколений.
- `Compiler/Compiler.cs` — начало поколения, подготовка полного набора ссылок и
  обработка конфликтов как обычных ошибок компиляции.
- `Compiler/PCU/PCUReader.cs` — корректное восстановление внешних ссылок из PCU.

## Оставшиеся ограничения и дальнейшая работа

- Полный специализированный прогон пока выполнен на Windows. Поведение файловых
  путей и регистрозависимость следует отдельно проверить на Linux.
- Явный полный путь непосредственно к reference assembly из каталога
  `Microsoft.NETCore.App.Ref` не является штатным сценарием Reflection-загрузки.
  Обычная директива с именем системной DLL разрешается в runtime implementation DLL.
- Для NuGet планируется использовать тот же выгружаемый проектный контекст, но с
  другой политикой инвалидирования: пакетные assets считаются неизменными до смены
  результата restore, тогда как локально разрабатываемые DLL проверяются перед
  каждой компиляцией.
- Будущий NuGet resolver должен явно выбирать compile/runtime assets по TFM и RID,
  учитывать транзитивный граф и `.deps.json`; простое сканирование каталога пакета
  для этого недостаточно.
