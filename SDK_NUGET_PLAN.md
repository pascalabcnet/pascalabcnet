# PascalABC.NET SDK и поддержка NuGet

Этот документ фиксирует направление развития проектной модели PascalABC.NET после унификации legacy-линии на .NET Framework 4.7.2 и modern-линии на .NET 10.

## Целевые платформы

Основное направление развития — `net10.0`: modern-компилятор, SDK и NuGet. Существующая линия `net472` сохраняется для Windows IDE и Linux/Mono IDE; расширение её поддержки NuGet не является обязательным этапом.

В исходном обсуждении рассматривались обе целевые платформы:

- `net472` — Windows IDE, Linux/Mono IDE и legacy-компилятор;
- `net10.0` — modern-компилятор и будущий SDK.

Директива `{$package Package.Id Version}` и правила разрешения версий остаются общими. NuGet resolver выбирает разные compile/runtime assets в зависимости от целевой платформы компиляции.

Работу с NuGet следует вынести в отдельный проект, например `PascalABC.NuGet`, первоначально для `net10.0`. Компилятор должен передавать ему целевой TFM, RID, список точных версий пакетов, источники и каталог NuGet-кэша. Дополнительная цель `net472` возможна при отдельной потребности.

## Единый результат restore

Restore формирует один граф для выбранной целевой платформы:

- compile assets (`ref`, затем совместимые `lib`);
- runtime assets;
- native assets для выбранного RID;
- resource assemblies;
- точные версии и абсолютные пути пакетов в NuGet-кэше.

Граф сохраняется в manifest, условно `Program.assets.json`. Один и тот же manifest используется запуском, отладчиком и публикацией. Повторно разрешать зависимости на каждом этапе нельзя.

На первом этапе не поддерживаются выполнение `install.ps1`, импорт `build/*.targets`, analyzers, generators и произвольные инструменты из пакетов.

## Режим Run: запуск без копирования зависимостей

Текущее состояние .NET 10: компилятор уже создаёт для программы с `{$package}`
`<имя>.deps.json` и дополняет `<имя>.runtimeconfig.json` путём к общему кешу
NuGet. Управляемые runtime-DLL и их транзитивные зависимости загружаются из
кеша при обычном `dotnet <имя>.exe`; копирование DLL и отдельный `pabcrun`
для этого сценария не требуются. Описанный ниже host остаётся вариантом
для будущих сценариев, прежде всего native/resource assets и иных целей.

Первоначально для режима Run предполагался служебный host без копирования
NuGet DLL в папку проекта или рядом с программой:

```text
pabcrun Program.exe Program.assets.json [аргументы программы]
```

`pabcrun` — внутренний runtime-host PascalABC.NET, а не часть публикуемой программы.

### .NET Framework 4.7.2

Это возможный дополнительный вариант, а не первоочередная реализация. Host должен:

1. загрузить manifest;
2. зарегистрировать `AppDomain.AssemblyResolve` до загрузки пользовательской программы;
3. сопоставлять полные имена сборок с точными путями в NuGet-кэше;
4. загружать известные managed assemblies через `Assembly.LoadFrom`;
5. настроить поиск native dependencies;
6. загрузить пользовательский EXE и вызвать его entry point;
7. сохранить аргументы, рабочий каталог, код возврата и STA-режим программы.

Поскольку программа запускается только из оболочки, зависимость от локального NuGet-кэша в этом режиме допустима. Перед запуском оболочка при необходимости выполняет restore.

### .NET 10

Можно использовать:

- host на основе `AssemblyLoadContext`; или
- `dotnet exec` с `--depsfile`, `--runtimeconfig` и `--additionalprobingpath`.

Если будет реализована поддержка обеих платформ, внешне команда и поведение оболочки должны оставаться одинаковыми.

### Отладка

Обычный запуск через `pabcrun` и отладка являются разными подсистемами. Сам по себе `pabcrun` не добавляет поддержку отладки .NET 10.

Текущий отладчик встроен в Windows IDE: `DebugHelper` напрямую использует `Debugger.Core.NDebugger`, а `Debugger.Core` получает старый интерфейс CLR через `mscoree.dll` и `CreateDebuggingInterfaceFromVersion`. Этот backend сохраняется для `net472`, но не считается backend-ом для CoreCLR/.NET 10.

В IDE необходимо ввести границу `IDebuggerBackend` (название условное):

```text
IDE (net472)
  -> LegacyDebuggerBackend -> существующий Debugger.Core -> .NET Framework 4.7.2
  -> CoreClrDebuggerBackend -> отдельный процесс/DAP       -> .NET 10
```

IDE при этом может остаться на `net472`: современный отладчик должен работать отдельным процессом и общаться с оболочкой по протоколу. Первым кандидатом для прототипа является NetCoreDbg с Debug Adapter Protocol; до принятия решения необходимо проверить совместимость, качество отображения Pascal-типов, комплект поставки, размер и лицензии всех распространяемых компонентов.

Для .NET 10 compiler должен выпускать portable PDB. Modern-backend запускает `pabcrun` либо непосредственно `dotnet` с тем же `Program.assets.json`, после чего отлаживает процесс, в который загружена пользовательская сборка. Необходимо проверить:

- точки останова и пошаговое выполнение;
- portable PDB, имена исходных Pascal-файлов и локальных переменных;
- отображение Pascal-типов и вычисление выражений;
- исключения и завершение процесса;
- console/WinExe режимы;
- STA для WinForms/WPF;
- аргументы и рабочий каталог;
- managed и native зависимости.

## Режим Publish: создание запускаемой папки

Для .NET 10 реализован первый вариант: команда **Программа → Опубликовать
.NET 10...** собирает текущий текст и создаёт `publish/<имя программы>/`
рядом с `.pas`. Туда копируются EXE, runtimeconfig, PDB при наличии, managed
NuGet DLL и замыкание явных `{$reference}`. Созданный NuGet `.deps.json` и
путь к общему кешу в runtimeconfig не переносятся: опубликованный EXE
запускается без локального NuGet-кеша. Папки программ разделены, поэтому
версии DLL не конфликтуют. Повторная публикация целиком заменяет прежнюю
папку программы. Поддержаны native-файлы Windows x64: выбор RID через NuGet,
описание в `.deps.json` для запуска из кеша и копирование при публикации.
Проверенные пакеты — Microsoft.Data.Sqlite 10.0.13 и MathNet.Numerics.MKL.Win-x64
3.0.0 с Math.NET Numerics/MKL provider 5.0.0. Тесты описаны в
`tests/NuGetRestoreTests/README.md` (`--native-assets`, `--sqlite-native`, `--mathnet-mkl`).
Проверен первый сценарий Microsoft.ML 5.0.0 под Windows x64: SDCA-регрессия,
прогноз, сохранение/загрузка модели в новом процессе, IntelliSense и публикация
без кеша/SDK (`--mlnet-regression`, `NuGet/Samples/MLNetRegression.pas`).
Пакетные копии базовых сборок согласуются с Microsoft.NETCore.App по identity
и версиям; старые копии не попадают в семантику, manifest и публикацию.
Локальные проверки этого правила входят в обычный прогон (`--framework-assemblies`).
Проверен нативный LightGBM под Windows x64 (Microsoft.ML.LightGbm 5.0.0,
LightGBM 4.6.0): обучение регрессии, фактический путь загруженной DLL,
сохранение/загрузка модели, IntelliSense, публикация без кеша/SDK/PATH и отказ
обучения без native DLL с восстановлением после возврата (`--lightgbm-native`,
`NuGet/Samples/LightGbmRegression.pas`). Прогноз по сохранённому дереву проверен
отдельно: он выполняется без native LightGBM. Для отсутствующей DLL в исходном
кеше учитывается предварительная проверка файлов manifest хостом .NET.
Остальные алгоритмы и нативные пакеты ML.NET требуют самостоятельных тестов.
Resource assemblies, нативные зависимости других платформ и self-contained
публикация остаются следующими этапами.

Для расширенной публикации (включая native/resource assets и другие цели)
планируется использовать полный граф и при необходимости создавать такой
каталог:

```text
Publish/
  Program.exe
  Program.exe.config
  Program.dll
  Program.deps.json
  Program.runtimeconfig.json
  package assemblies
  resource assemblies
  native dependencies
```

Набор файлов зависит от целевой платформы. В каталог копируется полное runtime-замыкание, но не compile-only assemblies.

Для `net472` на целевой машине должен быть установлен .NET Framework или Mono. Для `net10.0` сначала достаточно framework-dependent публикации; self-contained публикацию можно добавить отдельно.

Опубликованная программа запускается напрямую и не зависит от `pabcrun` или глобального NuGet-кэша.

## Архитектурная граница

### Пакеты в модулях: согласованные правила

Алгоритм рекурсивной компиляции модулей сохраняется: предварительный обход
всего графа не нужен. Все `{$package}` одного файла размещаются до любого кода
языка, включая `unit`, `program` и `uses`. Комментарии и другие директивы перед
ними разрешены. Требования файла обрабатываются вместе до его семантики и uses.

Граф зависимостей расширяется по мере подключения модулей. Одинаковые требования
не вызывают повторного восстановления. Если новый пакет требует заменить уже
подключённую DLL другой версией или содержимым, компиляция прерывается с понятным
описанием конфликта. Ранее выбранные DLL незаметно заменять нельзя.
Совместимые транзитивные ограничения новых пакетов разрешаются совместно;
явно заданные точные версии пакетов не переопределяются молча.

Обычные `{$reference}` и зависимости этих DLL участвуют в тех же проверках
общего графа: нельзя получить две разные сборки с одним внутренним именем.
Это не означает, что NuGet выбирает версию DLL, заданной явным путём.
Требования модулей должны также учитываться при чтении PCU. Будущие настройки
папки и проекта смогут задавать пакеты до начала компиляции.

Первый этап реализован: проверка размещения в modern-парсере, диагностика
с файлом и строкой, 46 проверок на каждой платформе. Legacy-поведение сохранено.
Восстановление пакетов из модулей и PCU, а также расширение общего графа —
реализованный следующий этап modern-компилятора. Требования очередного файла
восстанавливаются совместно с уже принятыми требованиями до его семантики и uses.
Повторение одной версии не запускает восстановление. Замена уже выбранной прямой
или транзитивной версии запрещена; конфликт с `{$reference}` проверяется по всему
накопленному набору сборок и их зависимостей. Совместное разрешение разных
совместимых ограничений сопровождается предупреждением.

PCU сохраняет прежний формат: требования берутся из существующих директив
заголовка. Чтение DLL родительского PCU отложено до обработки его зависимостей,
чтобы пакеты дочерних модулей были известны до чтения типов родителя.
Основной рекурсивный алгоритм компиляции исходников не изменён.
Проверки: [tests/NuGetRestoreTests/README.md](tests/NuGetRestoreTests/README.md),
режим `--module-packages`, также включённый в `--compiler`.
Внешний IntelliSense также учитывает пакеты из модулей. До построения DOM он
обходит реальные синтаксические деревья `uses` (обе секции и `uses ... in`),
готовит общий граф и проверяет конфликты с `reference`. Это отдельная подготовка
анализа, а не изменение алгоритма компиляции модулей. Для открытых файлов берётся
текст редактора, для закрытых — диск; без исходника требования читаются из PCU.
Изменение или удаление пакета обновляет зависимые подсказки; при конфликте старые
типы пакета не показываются. Проверки API и настоящего LSP: `--module-intellisense`
в NuGetRestoreTests (включены в обычный прогон, без сети).
Настройки папки и проекта пока не реализованы.

```text
{$package}
    -> требования очередного файла до его семантики и uses
    -> NuGet restore для выбранных TFM/RID без замены подключённых DLL
    -> ResolvedPackageGraph
         -> Run: manifest + запуск через pabcrun из глобального кэша
         -> Publish: копирование runtime-замыкания в выбранную папку
```

Существующие `IReferenceProvider` и подготовка ссылок являются точкой интеграции, но текущей модели «один DLL-файл одновременно для компиляции и запуска» недостаточно. Новая модель должна отдельно представлять compile, runtime, native и resource assets.

## Предлагаемый порядок реализации

Работа идёт по двум самостоятельным направлениям. SDK и NuGet могут разрабатываться студентами поверх консольного компилятора .NET 10 без встраивания в оболочку.

Для SDK/NuGet:

1. Определить формат `ResolvedPackageGraph` и manifest.
2. Создать NuGet resolver для `net10.0` и проверить простой пакет.
3. Реализовать запуск через `pabcrun` из NuGet-кэша.
4. Добавить транзитивные зависимости, resource и native assets.
5. Реализовать Publish в выбранную папку и регрессионные тесты.
6. Поверх этого развивать проектную модель PascalABC.NET SDK.

Для оболочки:

Ближайшая последовательность работ:

1. Выполнено: `commandmode` возвращён в оба консольных компилятора (`pabcnetc` и `pabcnetcclear`) для `net472` и `net10.0`; неиспользуемые ветки BinaryFormatter удалены, существующий протокол проверен, включая повторную компиляцию, передачу текста из редактора и настройки стандартных модулей. Проверка: [tests/CommandModeSmokeTest/README.md](tests/CommandModeSmokeTest/README.md).
2. После этого перенести независимый от редактора `PABCCompilerController` из `pascalabc-vscode/compiler-host` в Tooling вместе со сборкой, тестами и описанием JSON-протокола. В VS Code оставить клиент и упаковку готового компонента. Контроллер компиляции остаётся отдельным от LSP процессом.
3. Подключать Compile10/Run10 к старой оболочке после проверки этих компонентов; выбирать канал подключения на основании прототипа.

1. Начать с небольшого изолированного подключения долгоживущего компилятора .NET 10 через отдельные команды Compile10 и Run10. Выбор протокола требует сравнения существующего IPC и `PABCCompilerController`; компиляция не должна прерывать отдельный процесс IntelliSense.
2. Использовать существующий LSP-сервер для VS Code как основу внешних языковых сервисов. Выносить возможности встроенного IntelliSense по одной, дополняя сервер навигацией и поиском символов, и проверять соответствующее поведение клиента.
3. Сохранять возможность собрать и запустить основной проект без внешнего tooling. Интеграцию оформлять как дополнительный компонент.
4. Сделать отдельный прототип CoreCLR-отладки: запуск, breakpoint, step, locals, watch/evaluate и portable PDB; затем подключить выбранный backend к оболочке.
5. Рассматривать отдельную переработку графической оболочки после проверки внешних сервисов. Перенос PABCSystem и GraphABC не блокирует первые шаги.

## Linux-инсталлятор

Linux-инсталлятор является параллельной задачей и не должен блокировать SDK/NuGet. Первый практический формат — пакет `.deb` для Debian/Ubuntu с установкой среды в `/opt/pascalabcnet`, командой запуска, desktop-файлом, иконками и зависимостью от Mono. ZIP следует сохранить как portable-вариант. Поддержку RPM или универсального установщика можно добавить позднее.
